# Oh My Shine!

Независимый бренд одежды, аксессуаров и подарков, декорированных вручную стразами. Сайт на первом этапе — **витрина и приём заявок**, а не полноценный интернет-магазин.

> **Главный принцип:** сначала проверяем спрос и процесс выполнения заказов с минимальными затратами; полноценный checkout, корзину и WooCommerce добавляем, когда они действительно понадобятся. Не строим инфраструктуру «на вырост» ценой усложнения MVP.

## tl;dr

```bash
pnpm dev                # локальный dev-сервер
pnpm assets:images      # обработка изображений существующим скриптом
pnpm assets:icons       # сборка SVG-спрайта существующим скриптом
pnpm build              # production-сборка в dist/
```

## Продукт и границы первой версии

- **Один сайт для Черногории и международных покупателей.** Международная доставка и доступность конкретных направлений должны подтверждаться до обещания покупателю срока и цены.
- **Все товары показываются на главной странице (`/`).** Отдельного каталога, страниц категорий, карточек товаров с собственными URL и корзины в MVP **нет**.
- Действия с товарами ведут к заявкам: вопрос, запрос на индивидуальный заказ или оформление заказа через форму. Заявка **не является оплаченной покупкой**.
- Базовая модель включает изделия в наличии и изделия, изготавливаемые под заказ; срок изготовления показывается отдельно от срока доставки.
- Первоначальная валюта — **EUR**. Языковая архитектура должна допускать **SR/ME, EN, RU**.
- Страницы, необходимые для доверия и юридической прозрачности (доставка и возврат, уход, индивидуальный заказ, контакты, конфиденциальность и условия), добавляются по мере готовности.

## Технологический стек

| Область   | Сейчас                                                                   | Позже, если потребуется                                       |
| --------- | ------------------------------------------------------------------------ | ------------------------------------------------------------- |
| Сборка    | **Vite 8**, многостраничный статический сайт                             | Vite остаётся сборщиком CSS/JS для темы WP                    |
| Разметка  | Обычный **HTML**                                                         | PHP-шаблоны WordPress / WooCommerce                           |
| Стили     | **CSS + PostCSS**, существующие `@layer`, `@scope`, переменные и миксины | Те же CSS-файлы                                               |
| Скрипты   | **ES modules / JavaScript**                                              | Те же модули; TypeScript точечно при росте логики             |
| Интерфейс | Без обязательного React, Astro, Pug или SPA                              | React только для сложных автономных виджетов                  |
| Хостинг   | **Cloudflare Pages** (план)                                              | Хостинг с PHP и MySQL/MariaDB для WP                          |
| Заявки    | **Cloudflare Pages Functions** (план)                                    | WP REST API либо отдельный сервис заявок                      |
| Commerce  | **Формы, без онлайн-оплаты**                                             | **WordPress + WooCommerce** и согласованный местный эквайринг |

**Не добавлять сейчас:** Astro, Next.js, отдельную CMS, корзину, собственный checkout, WordPress, MySQL, платёжный SDK или обязательный React.

## Локальная разработка

Нужны Node.js, совместимый с установленной версией Vite, и pnpm. Использовать менеджер пакетов проекта; не смешивать `npm`, `yarn` и `pnpm` lock-файлы. При появлении `pnpm-lock.yaml` сохранять его в Git.

```bash
pnpm install            # установить зависимости
pnpm dev                # локальный dev-сервер
pnpm lint               # ESLint + Stylelint
pnpm lint:js            # только JavaScript
pnpm lint:css           # только CSS
pnpm format             # форматирование исходников (изменяет файлы)
pnpm build              # production-сборка в dist/
pnpm preview            # локально просмотреть собранный dist/
pnpm check              # lint + build
```

Подготовка ассетов при наличии исходных материалов:

```bash
pnpm assets:images      # обработка изображений существующим скриптом
pnpm assets:icons       # сборка SVG-спрайта существующим скриптом
```

Эти команды **не должны** бесконтрольно запускаться при каждой сборке, если их входные директории ещё не подготовлены. Перед деплоем запускать как минимум `pnpm check` и проверять страницу вручную на мобильном и десктопном экранах.

### Добавление страниц

- Главная остаётся в корневом `index.html`.
- При появлении контентных страниц использовать `delivery-and-returns/index.html`, `care-guide/index.html`, `custom-order/index.html` и т. п.
- Для каждой новой страницы **добавлять точку входа в конфигурацию многостраничной сборки Vite** и проверять прямое открытие URL на хостинге. Текущий `vite.config.js` пока рассчитан на главную страницу; наличие папки с HTML само по себе не гарантирует попадание новой страницы в `dist/`.
- Не размножать общую разметку header/footer вручную на множество страниц. Когда повторение станет проблемой — выбрать минимальный шаблонизатор или сборочные partials, ориентируясь на переносимость HTML в PHP. Pug не является обязательным.
- Не добавлять клиентский роутер ради статических страниц.

## Формы и заявки

**Текущее состояние:** в `index.html` уже есть формы, направленные на `POST /api/request`, в том числе формы с вложениями (`multipart/form-data`); клиентская логика находится в `src/js/form.js`. **Серверного обработчика в текущем проекте нет. Формы нельзя считать работающими.**

План реализации:

1. Создать `functions/api/request.ts` для Cloudflare Pages. При локальной разработке тестировать API в среде Cloudflare (например, через Wrangler), а не предполагать, что простой `vite dev` обслуживает `/api/request`.
2. Проверять обязательные поля, тип/размер/число файлов и согласие на обработку данных **на сервере**; браузерной проверки недостаточно.
3. Включить защиту от спама и злоупотреблений (например, Turnstile и ограничения запросов). Никогда не доверять присланным ценам, SKU и названию товара как окончательным коммерческим данным.
4. Выбрать подтверждённый способ доставки заявки владельцу и хранения вложений. Email-уведомление само по себе не является надёжной базой заявок; для хранения можно рассмотреть Cloudflare R2/D1 после оценки стоимости и политики хранения.
5. Возвращать определённый JSON-ответ и показывать реальный результат пользователю. Не отображать «Заявка отправлена» до успешного ответа сервера.
6. Предусмотреть сроки удаления персональных данных, сведения о конфиденциальности, защиту секретов и контроль доступа к файлам. **Не хранить** банковские реквизиты карт или другие платёжные данные.

По возможности сохранять стабильный контракт API и независимость UI от его реализации: сейчас Cloudflare Function, позже WordPress REST endpoint или отдельная служба. При будущей смене бэкенда адаптируется сервер, а не весь интерфейс формы.

## Контент, изображения, SEO и локализация

- Экспортировать оригинальные изображения из макета в подходящих размерах; соблюдать точность декора и внешнего вида реальных изделий. Не использовать несоответствующие товару изображения.
- Для веба: оптимизированные форматы, `width`/`height`, `srcset` по необходимости, осмысленный `alt`, lazy loading для изображений вне первого экрана.
- Хранить понятные **стабильные ID/артикулы** товаров и не связывать их с порядком элементов на странице или текстом названия. Позже это упростит импорт в WooCommerce.
- Даже если все изделия представлены на `/`, каждая карточка должна иметь однозначный идентификатор и передавать его в заявку.
- На старте использовать одну валюту EUR и явно показывать, что доставка/ввозные сборы могут рассчитываться отдельно. Не обещать worldwide shipping без проверенных маршрутов.
- Подготовить структуру для языков SR/ME, EN, RU. У каждого опубликованного языка должны быть корректные `lang`, метаданные, canonical и при необходимости `hreflang`.
- Не забыть страницу политики конфиденциальности, условия заказа, доставки и возврата; конкретные формулировки и налоговые обязательства подтвердить у черногорского специалиста.

## Развёртывание

Предполагаемая платформа для MVP — **Cloudflare Pages**:

- команда сборки: `pnpm build`;
- выходной каталог: `dist`;
- серверные обработчики: корневой `functions/` в репозитории;
- секреты API — только в серверных переменных окружения Cloudflare, не в `VITE_*` и не в клиентском коде;
- перед запуском проверить HTTPS, редиректы, прямые URL страниц, 404, мобильную версию и **реальную доставку тестовой заявки**.

Домен, почтовый провайдер, хранилище заявок и модель доставки пока **не утверждены**. Отсутствующие интеграции не заменять заглушками, создающими видимость оплаты или принятого заказа.

## План перехода к WordPress / WooCommerce

Переход возможен, но **не является обязательным следующим этапом**. Триггеры: регулярные оплачиваемые заказы, сложные остатки и варианты товаров, необходимость самостоятельного управления ассортиментом, купоны, возвраты, автоматизация доставки или полнофункциональная онлайн-оплата.

Предполагаемый путь:

1. Подтвердить, что черногорское юрлицо может подключить подходящий эквайринг (например, NLB или другой банк/провайдер), включая оплату иностранными Visa/Mastercard; уточнить комиссии, возвраты и интеграцию с WooCommerce **до реализации checkout**.
2. Развернуть WordPress + WooCommerce на хостинге с PHP и БД в отдельной staging-среде.
3. Создать собственную тему, сохранив действующие CSS, JS, ассеты и максимально возможную HTML-разметку. Vite остаётся сборщиком фронтенда.
4. Перенести товары с сохранением артикулов/slug, изображений, вариантов и маршрутов; все товары **могут по-прежнему показываться на главной**. Отдельная страница каталога необязательна и появляется только при продуктовой необходимости.
5. Перевести формы и заказы на согласованный процесс; **не** писать собственный платёжный checkout и не считать редирект браузера подтверждением оплаты — нужны проверенные серверные подтверждения платежей.
6. Проверить SEO-редиректы, формы, статусы заказов, возвраты, налоги и доставку до переключения домена.

**Что переносится:** CSS, JS-модули, изображения, большая часть HTML и идентификаторы товаров. **Что потребует адаптации:** HTML в PHP-шаблоны/WordPress blocks, рендер товаров, формы, система заказов, checkout и хостинг. «Совместимость с будущим WooCommerce» не означает, что статические HTML-страницы автоматически станут темой WordPress.

## Правила принятия решений

1. **Спрос и продажи важнее технической сложности.** Никаких крупных платформенных миграций без конкретной бизнес-причины.
2. **Сохранять существующую архитектуру CSS и JS.** Рефакторить по необходимости, а не ради модного стека.
3. **Все товары на главной** до отдельного решения о каталоге.
4. **Не внедрять корзину и оплату раньше эквайринга.** Приём заявки не равен приёму денег.
5. **Разделять интерфейс и серверные интеграции.** Формы, уведомления, платежи и данные товаров не должны быть тесно связаны с конкретным хостингом.
6. **Не выдавать планы за реализованные функции.** В README и интерфейсе явно различать «работает», «проектируется» и «не подключено».
7. **Каждое изменение проверять:** lint, production build, основные интеракции, доступность, мобильные экраны и ошибки API. Не оставлять скрытых ошибок и фиктивных успешных состояний.

---

**Принятое решение:** статический Vite-сайт, товары на главной, заявки через формы. **Возможная эволюция:** WordPress + WooCommerce без полной замены фронтенда. Любые изменения этой стратегии сначала фиксировать здесь и в `AGENTS.md`.
